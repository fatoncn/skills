# 通用编排指导

本文件记录分工、任务书、审核、验收与收尾指导，适用于用户或项目规则选定的编排工作。它不依赖 Foreman 初始化；走宿主子 agent 时可直接使用。

用户明确要求亲自执行、不派发或指定通道时，遵循该要求。不要因为普通请求出现“调研”“排查”“review”等词就启动外派。通道、角色档位及确认策略见下文。

按当前阶段阅读：分工与通道、阶段 0–2（对齐与任务书）、阶段 4（审核与验收）、阶段 5（收尾）。仅需模板时读 [任务书与交付模板](issue-pr-flow.md)；仅在实际调用 Foreman 执行器时读 [外派操作手册](foreman-operations.md)。

## 核心口径

**核心口径：编排层统筹，执行层干活。** 你是编排层，只做四件事：需求分析、规划（拆票、写任务书、定契约）、推进（派活、答疑、收敛）、审核（增量代码逐行读，方法在阶段 4）。用户选定通道（foreman 或 spawn）之后，**所有能独立切分的执行工作都交给执行层**：拆票前的排查与调研、实现、复审、验收冒烟、收尾，都是执行工作。拿 bug 举例：排查交给执行，下判断交给编排。留给自己的只有三类：要用只有本会话才有的东西（会话上下文、会话里的 MCP、编排者所在 agent 自己的能力，如 Claude 的 Artifact）——**需要编排层独有能力的活不能交给 foreman**，执行者拿不到这些，派过去只会卡住；要与用户来回确认口径的判断；一两步就能做完的小事。已有口径能覆盖的小风险决定你直接拍板并说一句按的哪条，拿不准的问用户要口径。

每张票都要有「完成定义」：实现票是一组能跑的、退出码说了算的命令；调研票是交付物清单（要核哪些事实、给什么格式的锚点），验收是逐条核。写不出完成定义的先把问题定清楚，不派。

## 角色与模型档位

按**档位描述**选模型，不绑死模型名（模型会迭代，`doctor` 打印当前可用模型与推理档）：

| 角色 | 干什么 | 档位描述 | Codex 对应（2026-09-11） | Claude 对应（beta） |
|---|---|---|---|---|
| `implement` | 实现、补测试、接线等一切写码活；`run` 默认 | 旗舰或次旗舰 + medium | gpt-5.6-sol / medium | sonnet / high |
| `review` | 对抗性复审：只看 diff，挑破坏项目约定 / 仓库约定 / 最佳实践的地方，只提意见你拍板；永远新线程、只读沙箱；`review` 用 | 旗舰 + medium | gpt-6-astra / medium | opus / xhigh |
| `mechanical` | 轻活：按既定契约接线、补测试、改文案、批量重命名，不做设计取舍；`run --role mechanical` | 次旗舰 + low～medium，便宜但精准 | gpt-5.6-terra / medium | sonnet / low |
| `research` | 只读调研：排查、核事实、找锚点、复现，交事实清单不下判断；`run --role research --writable <交付目录>` | 旗舰或次旗舰 + high | gpt-5.6-sol / high | opus / high |
| `accept` | 验收：把产品真跑起来对清单看，证据落交付目录，发现问题只报不修；`run --role accept --writable <证据目录>` | 旗舰或次旗舰 + high（比实现者高一档，假「通过」最贵；多是浏览器脏活） | gpt-5.6-sol / high | sonnet / xhigh |

## 分工：编排层统筹，执行层干活；派给谁由用户定

分工是**两级决定**。

**第一级：这段活是统筹还是执行。** 统筹（需求分析、规划、推进、审核）是你的，执行都派出去。判断的对象是**每一段活**，不是整个任务判一次：拆票前的排查、写任务书要核的事实、实现、复审、验收冒烟、查库比对、收尾，每一段开始前先问一句「这是统筹还是执行」。执行者同样值得信任：它读的是同一份项目规则（codex 自动读项目根 `AGENTS.md`），走的是同一条审批链；差别只有模型弱一档、上下文窄一些，所以模型弱一档兜不住的判断（拍板、取舍、契约）留给自己或用户，事实与产出交给它。

- **适合派出去**：批量且可并行的信息收集与检索（多 PR / 多仓库 / 多文件 / 多日志源逐条核对）、范围明确的复现与验证、开销大但结论短的探查、彼此独立的机械改动、目标与验收明确的实现或方案任务。查生产、读凭证、跑本机 CLI 不是留给自己的理由：任务书点名动作、写死边界（只读还是可写、动哪张表、怎么回滚），产出按阶段 4 逐条核。
- **留给自己**：只有开头那三类（要本会话独有的上下文或 MCP；要与用户来回确认口径；一两步的小事）。合并动作由人按，是项目规则，与派不派无关。
- **拿 bug 举例**：复现、定位、查数据形状、找在途 PR 的重叠面是排查，派出去；根因成不成立、修不修、怎么修、要不要另开票是判断，你下。

**第二级：派 spawn 还是派 foreman，开工前由用户定，不由你按判据自动路由，也不预设默认。** 两条通道地位相同，只是各自擅长不同。会话开头、派出第一项执行工作之前，**必须让用户在两条里选一条**作为本会话的通道（用户开头已声明的不再问）；之后本会话沿用，用户中途改口按新口径，用户为某项活单独指定的按用户的。你觉得某项活更适合另一条，**提一句建议让用户定**，不自作主张切换。被选通道走不通时（foreman：执行器不可用、需要编排层独有能力、本机还没做完「第一次用」；spawn：需要 OS 沙箱或第二模型视角）告知用户，等还是改道由用户定。「活小」不是自己做的理由——编排者自己动手的上限只有一条：已知文件或符号的一两条 grep、读一个文件（单点核对）；超过这个量就是调研，派出去。

| 通道 | 怎么派 | 它有什么 | 代价 |
|---|---|---|---|
| **外派 foreman**（codex 主线 / claude beta） | `$FOREMAN run` | 独立 worktree + OS 沙箱；线程可续、返工记得上一轮；第二模型视角；`report` 事后越界探针；本机凭证、CLI、网络经「替我审批」放行后都能用；调研走 `--role research` | 吃 codex 订阅额度（与用户自己的 Codex 共享）；一轮 20～40 分钟；看不到你的会话上下文和你的 MCP |
| **宿主 spawn 子 agent** | 宿主自带的子 agent 机制（Claude Code 是 `Agent` 工具，Codex 是它的子 agent；默认次旗舰模型，如 `opus`） | 快、便宜；看得到你的上下文与工具；追加指令续同一个 agent（Claude Code 用 `SendMessage`） | 同源模型视角单一；没有 OS 沙箱，只有权限模式 |

各自擅长，给用户定通道时参考（不是路由判据）：

| 活的类型 | 更顺手的通道 | 为什么 |
|---|---|---|
| 产出代码进 PR、完成定义能机械判定、1～3 小时量 | 两条都行 | foreman 多一层 worktree 隔离与第二模型视角、线程可续返工；spawn 起步快、看得到你的上下文 |
| 排查、只读调研、跨很多文件读、复现核实 | 两条都行 | spawn 固定成本低、看得到你的上下文；foreman 走调研线程（`--role research`），有第二模型视角、线程可续追问 |
| 要连库、读 Keychain、跑本机 CLI | 两条都行 | foreman 执行者经「替我审批」放行后一样能用，任务书点名动作即可；只有要用编排者会话里的 MCP 才必须 spawn |
| 验收 PR：浏览器 / 真机 / 部署环境冒烟（阶段 4 的四种情况内） | 你自己、spawn 或 foreman 的 `accept` 线程 | 实现者不验收自己的活；派谁由用户定 |
| codex 额度告急（`doctor` 看百分比）、并发到上限或执行器不可用 | 问用户：改 spawn 还是排队 | 不为了省额度降沙箱、改权限、换 `--full-access` |

**互斥**：两条对同一项活互斥，选定就走到底。**同一条分支 / worktree 同时只有一个执行者**，不分通道：不能同时有 foreman 执行者和 spawn 子 agent，不能让子 agent「顺手帮 codex 修一下它的 worktree」，派新活前确认前一个已停手（`git status` 干净只说明此刻没人在改）。foreman 侧脚本强制：同一 PR 上另一条线程还在 RUNNING / QUEUED / WAITING 时 `run` / `review` 拒绝。同一批次里不同的活走不同通道是正常的，但每项活走哪条由用户定。

### 两条通道通用纪律

- 派发的子任务必须**自包含**：目标、涉及路径、边界（只读还是可改）、期望返回的结论格式。要结论和关键证据，不要文件内容转储。同一份任务书两条通道都能用。
- **执行方的结论按输入证据对待，不是真值**：数字、口径、线上状态要自己复核。最终落地与对用户的结论由主会话负责。产出不分通道都走阶段 4 的验收，不因为「同源」就少看。
- 已派出去的活不重复再跑；需求或任务中途改了，在跑的线程不会自己看到，foreman 默认立刻 `steer` 通知（纠偏、撤回、下一轮预告都算），再用 `tail` 看到它确认并改了方向才算送达。只有变化与本轮无关、留到下一轮不会造成两轮改同一处，才用下一轮 `run`；工具阻塞提问用 `answer`。spawn 用 `SendMessage` 给同一个 agent。

### spawn 通道的具体规则

- 子 agent 默认次旗舰模型（主会话跑旗舰时显式传 `model: "opus"`），只有用户要求或子任务确需更强推理才升级。
- 多个互不依赖的子任务**在同一条消息里一次性并发派发**。
- 权限边界：不为子 agent 单独放宽权限模式，它跟随主会话的权限模式；改代码的子 agent 也只在自己的 worktree 或当前检出里改，不碰别人的 worktree。

## 阶段 0 · 对齐意图（不可跳过）

拆之前先和用户确认：**目标是什么、边界在哪、什么算完成、基点分支是什么**。
拆解方案（票清单 + 每张票的完成定义）**先给用户过一遍再开工**——执行者是花额度且会改代码的，拆错返工成本高。
已有口径能覆盖的小风险决定直接拍板，写成「默认执行、不同意再说」并注明按的哪条；只上报既定口径覆盖不到、需要产品判断的决策，拿不准的问用户要口径。一份方案拍板点 ≤3 个。

## 阶段 1 · 拆解与背景文档

### 先核事实：够量就派调研线程

拆票前要核的事实：最新 base 上的现状与锚点（文件:行号）、数据形状（库里长什么样）、在途 PR 碰了哪些文件、能不能复现。这些是执行工作：够量（要翻十几个文件、要查库、要复现）就先派一张调研票（按会话定的通道：foreman 调研线程或 spawn 子 agent），交付事实清单，你拿着它拆票；只有一两步的小核对自己看。Foreman 调研线程的走法见 [外派操作手册的阶段 3](foreman-operations.md#阶段-3--派活)，任务书模板 `research-<id>.md` 见 `issue-pr-flow.md`。

**先拍板再派**：架构取舍、契约设计；需求含义未定；只能靠人眼判断的（UI 观感、文案）——这些是模型弱一档兜不住的判断，契约由你写定再派。数据库 schema 变更走项目自己的流程。

### 拆解规则（pi-fleet 实测教训，照守）

1. **按文件边界切，不按功能层切。** 两张票改同一文件 = 合并或串行。登记点（router barrel、写入方登记表、契约 index）是并发的固定成本，派活时就预期到，别为它合票。
2. **文件不重叠 ≠ 合并后不炸**：符号级耦合（A 把函数搬走、B 从旧位置 import）单票各自全绿、合起来才炸。允许搬符号的票要么禁止搬，要么把「原位 re-export」写进完成定义；**收口后在合并树上再跑一次全仓 type-check**。
3. **契约先行**：A 依赖 B 的类型 / 签名时，把契约写进背景文档定死，两边照着写，契约由你写。
4. **每张票 1～3 小时人类工作量**；有依赖就分批，第一批全部验收通过再放第二批。
5. **一个用户可感知的问题 = 一张 issue**，哪怕根因分散多处；开票前先搜已有票，有就扩容不新开。
6. **PR 粒度按「一次 review + 一次验收能覆盖的用户面」拆，不按组件 / 阶段拆**；每批 2～3 个 PR。硬约束才拆：数据库变更走项目自己的流程、两块确实互不相关。
7. **不要在任务书里给「已知环境噪音」的文件名豁免清单**，给方法：与基线逐条比对失败集合。
8. **在最新 base 上拆票**：核现状的人（多半是调研线程）必须看 `origin/<base>`（`bootstrap --no-install` 的检出就是它），不在主 checkout 的旧分支上 grep——主 checkout 常落后上千提交，会把「没有这个页面」这类误报写进任务书。
9. **追加范围前先看在途 PR 的 diff**：碰同一片文件的开着的 PR 有哪些、各改了什么，是调研票的固定一问；你拿结果决定是扩它还是新开票，防止两条线改同一处。

### 背景文档

一份，全批共享，会注入每个执行者的开发者指令（`bootstrap --context`）。**写事实和契约，不写鼓励**，每一句都在花每个 agent 的 token。模板见 `issue-pr-flow.md`。**落点按项目规则**：项目说中间产物放哪就放哪，任务书、返工说明、验收包同放；项目没规定时建议 `~/.foreman/projects/<项目>/batches/<批次>/`。都不进仓库。

## 阶段 2 · 任务书与实现真源

**真源不限于 issue**：GitHub issue、需求 / 方案文档、用户在会话里给的口径，都可以是一张票的真源。规矩只有一条：**任务书首段写明真源，每个 PR 描述注明实现真源**（issue 链接 / 文档链接 / 用户口径原话加日期），让验收和复审有东西可对。

任务书按 `issue-pr-flow.md` 的模板：真源 / 目标 / 背景 / 范围（可改与不可改）/ 要求 / **完成定义** / 风险档 / 红线。人和执行者读同一份。

写任务书的四条戒律：
- **不自造数值约束**：任务书里的每个数字（尺寸、阈值、条数、超时）都要有出处（真源、设计稿、现状代码）；没有就写「沿用现状」或「按设计稿」，不要为了显得具体编一个。
- **UI 判据写成产品口径**：元素何时出现 / 不出现按用户可感条件写（「本组已完成时」），不写成实现字段映射（`taskMode === …`）；映射由执行者对着代码定，写错了是它的活。
- **写日期先跑 `date`**：真源行、收尾任务书、验收包的时间戳先看系统时间再写。
- **不赘述固定拼接层已有的内容**：每轮 prompt 前面固定拼着「本轮位置」块、角色文件（位置、沙箱、分工边界、提问方式、输出格式）、批次背景、claude 的引擎事实、收尾轮的收尾契约；这些里已有的，任务书、复审关注点、收尾任务书都不再写一遍（不重复输出格式、不重复「只改本轮目录」、不复述项目规则），只写本票特有的：真源、目标、范围、要求、完成定义、口径。所有角色都适用。

建 GitHub issue 是**建议**而非前置：需要跨会话追踪、多人可见、或项目规则要求时再建，issue 正文就用任务书。建的话：
- 项目规则规定了 issue 首行契约的（如「需求: <编号>」），适用的票**第一行**必须是它；不适用的不写，**不要编造**。
- 建 issue 由你直接做，不用先问（每张票都要走的常规对外动作，可改可关）；批量建的把标题清单在回复里列一遍即可。
- 票的标题写用户可感知的问题，不写内部模块名；一个问题一张票，已有票就扩容不新开。

## 阶段 4 · 验收（你的核心工作）

**不要相信执行者的 DONE。** 也**不要相信派生产物的「不存在」**：快照、`gh` 列表、CI 结论都是影子，读之前先问「它截止到什么时候」。

验收顺序保持为运行报告、机械检查、代码差异；机械没过就别读代码。

Foreman 通道的对应命令见 [外派操作手册](foreman-operations.md#验收与收尾命令)。

Foreman 运行报告的阻塞信号见 [外派操作手册](foreman-operations.md#验收与收尾命令)。

### 机械全绿之后：复审给对抗性意见，需求符合度你自己审

Foreman 通道的对应命令见 [外派操作手册](foreman-operations.md#验收与收尾命令)。

**复审不判「需求做对没有」**——复审者没有你的上下文，判不了。它的活是**对抗性视角**：这次改动有没有破坏项目约定（项目根 `AGENTS.md`）、仓库约定（仓库内 `AGENTS.md`、周边代码的写法）、最佳实践；给的是**意见 + 依据**（哪条约定、哪个实践、什么输入会出错），不是判决，采不采纳由你逐条拍板。它最需要的上下文是你写的需求口径，**给得越多视角越全**：为什么做、做到什么程度、哪些是有意不做的，再加用户原话（带日期）、会话里定过的口径与否决过的方案、相关 issue / 文档链接、批次背景（复审线程不自动注入 `--context` 的背景文档，要么贴路径要么摘要点）、上一轮复审采纳 / 不采纳的决定——没有这些它只能对着 diff 猜，把权衡后的边界当遗漏报。它自动拿到的是角色文件、上一轮任务书、执行者交付报告和完整 diff，这些不用再贴。它顺带交一张「要求 → diff 位置」对照表，那是给你逐行审用的索引，不是结论。它另交一节「与原口径的对齐风险」：把 diff 的实际行为对回你给的需求口径与用户原话，列出对不上的地方；那是风险清单不是判决，要求它客观、不夸大、拿不准就标「不确定」；你审需求符合度时从它开始核，逐条判成立不成立。**按风险档决定跑不跑**：低风险（约 ≤50 行、不碰 prompt / 数据写路径 / 迁移 / 权限 / 计费 / 并发）跳过复审，靠你逐行审加测试 / CI；中高风险必跑。模板见 `issue-pr-flow.md`。

**需求符合度由你审，谁都替不了**：①改的是不是要求的那件事（对完成定义逐条核）；②有没有作弊；③有没有留垃圾（退化 helper、零调用旧函数、只剩壳的抽象）。

**审核范围**：审核 = 逐文件读完全部 diff（含 SQL、配置、测试）并逐条对照任务书，不得靠执行方摘要、PR 描述、CI 绿、review 线程数替代；任务书之外的行为改动一律点名报告并阻塞。首轮读全部；第 N 轮只审上一轮之后的增量（`git diff <上轮 head>..HEAD`），剔除同步 base 带进来的部分；收尾后推的增量与同步 merge 也要逐行读。整文件删除按文件名核对「该删的都删了、不该删的没删」，不逐行读被删内容；新增与修改逐行读。这一步是编排层的活，不外派。

**真实浏览器 / 真机验收默认不做**（cookie 09-13）：验收默认靠单测、集成测试、CI 与你的逐行审；只有四种情况才上真实浏览器——用户明确要求、破坏性重构、大型功能开发、较大的产品口径调整。要做时走 `accept` 线程：机械与代码审过之后，把产品真跑起来对着清单看的活派出去：

Foreman 通道的对应命令见 [外派操作手册](foreman-operations.md#验收与收尾命令)。

验收者按清单逐项操作、证据落交付目录、不在范围项只记不判、发现问题只报不修；交回来的是填好的 `ACCEPT-<PR>.md` 和逐项结果，可不可合由你判。派谁（自己、spawn、foreman 的 `accept` 线程）按会话定的通道，用户指定的优先。任务书模板 `accept-brief-<id>.md` 见 `issue-pr-flow.md`。

**调研票的验收**：交付物按任务书的问题逐条核：每条事实有没有出处（文件:行号、命令与输出）、「看到的」和「推断的」分开没有、未核项列了没有；关键数字与线上状态自己复核一次再采信。判断由你下：调研者给的是候选项和证据，不是决定。`report` 的越界探针对调研票同样有效：改到检出里的文件一律阻塞。

### 返工

把问题写成新 prompt 再 `run`：贴失败命令原文输出、文件行号、期望行为。**不要只说「还是不对」**。同一张票验收不过、返工超过 3 轮不收敛就停：拆错了或不该派，告诉用户。

## 阶段 5 · 收口：PR、review 闭环、报可合

执行者只在 worktree 里 commit；**首次 push / 建 draft PR / 建 issue 由你直接做，不用先问**（cookie 09-11：每张票都要走的常规对外动作、没有破坏性，编排者自己拍板；仍要人按的只有项目规则点名的：合并由人、生产 / 动钱 / 部署平台的写操作、改写共享历史、删远端分支）；之后收尾轮的 push、回复 review 由实现者按收尾契约做（`run --closeout` 默认续目标 PR 最近的 `implement` / `mechanical` 实现线程，显式 `--role` / `--thread` 优先）：

Foreman 通道的对应命令见 [外派操作手册](foreman-operations.md#验收与收尾命令)。

以下是默认口径，项目规则有规定的按项目的：

- PR 默认 draft（`github.pr_draft`），CI 绿、描述完整（含「复测入口」节、风险档；项目要求的实测证据节按项目规则）后再收尾转 Ready。收尾由实现者续同一线程（`run --closeout`）。
- **review 机器人反馈按风险分档处理 1～2 轮**：低风险（约 ≤50 行、不改 prompt、不碰数据写路径 / 迁移 / 权限 / 计费 / 并发）1 轮，只修成立的 high / medium；中高风险最多 2 轮，第 2 轮只修第 1 轮修复引入的新 high / medium。low / nit 回复 + resolve 不 push；每轮攒齐一次 push；到上限列表交人拍板，不进第 3 轮。同步 base 的 push 不算一轮。
- **执行者不等 CI**：收尾轮 push 并回复 / resolve 本轮线程后立即交报告结束，不等待这次 push 的 CI 或下一轮 review。编排者用宿主的后台命令（Bash `run_in_background` / Monitor）轮询 `gh pr checks` / `gh run view` 的当前 head；CI 红了或出现新 finding，再派下一轮收尾，不让执行者 turn 前台空等。
- **没有 CI run 先查冲突**：PR 一个 run 都没有多半是和 base 冲突了，不是在排队（不少仓库 feature 分支只走 pull_request 触发）；解完冲突再等。
- **报「可合」前重数当前 head**：unresolved threads + 最新 summary 评论；review job 绿 ≠ 0 findings、红 ≠ 有 findings（0 字节产物 = 没评上，自己补审）。base 前进过且同模块有删词条 / 改签名的，先 merge base 重跑再报。
- **小修轻量收尾**：改动约 ≤50 行、不改 prompt 的修复，不做全范围复审、不写闭环表格、不重复 preview 自证；push 后一句话报 head 与一条证据，真实复测交给合测做一次。
- **返工复测按改动性质分两档**（cookie 09-12，09-13 收紧）：验收通过后的返工轮不重跑整套冒烟；只有这张 PR 本就在真实浏览器验收范围内（阶段 4 的四种情况）且返工项**用户可见**（页面、导航、交互、用户能看到的数据与文案）时，才在报可合前补一次**增量 Preview 冒烟**——只点被改的那几条路径（十分钟级），多轮返工的可见项攒到最后一轮一起点，派 `accept` 线程或并入合测；其余返工靠钉住该行为的单测 + CI，不上浏览器。
- **批次合测只做集成态冒烟，上不上真实浏览器按阶段 4 的四种情况判**：执行者的开发自测（单测、类型检查、prompt 抽样、本 PR 触碰的面）回答「改动做到了它说的事」；合测回答「用户流程走得通、没有非预期问题」，两层不互相替代。合测只核「合并后每个 PR 的效果都在、受影响主流程走通一遍、同一片代码没互相打坏」，不重跑执行者已自证的项；只有回归和流程走不通判阻塞，批次外既有问题只记不判。合测任务书按此写，不复制单 PR 的验收清单。
- **报「可合」= PR 链接 + 复测入口**（有预览 / 测试环境就给 URL 和从哪进）；用户亲自验收还要**证据（截图或输出）+ 分段操作流程 + 已知不在范围项**（`ACCEPT-<PR>.md`，模板见 `issue-pr-flow.md`；由 `accept` 线程填好、你核过再给）。
- **合并动作由人执行**：你报可合然后停，不跑 `gh pr merge`；「先合了」「允许绕过 CI 直接 merge」都不改变谁按键，听到像放宽的话先复述确认一次。
- `Closes #N` 在 PR 不进默认分支时不生效：合入后自己关票并留评论。
- 每合一条线在汇总分支跑一次全仓 lint / type-check；合入前把最新 base 合进来重跑。
- **清理 worktree 前查未推送提交**：`cleanup` 会拒绝有未提交或未推送改动的 worktree（PR 已 MERGED 的分支最容易骗人——合并后又追加的 commit 会悬在那里）。
