# issue → worktree → 线程 → PR：模板

九份东西，职责不同，别混。**干活纪律都在这些文件里由编排者写；注入执行者的角色文件（`~/.foreman/roles/<名>.md`，样例在 `assets/roles/`）只写契约：位置、沙箱事实、分工边界、提问、输出格式。**

| 文件 | 注入 / 投递方式 | 内容 | 谁读 |
|---|---|---|---|
| `BACKGROUND.md` | `bootstrap --context`，进每个执行者的开发者指令（全批共享） | 这批活的整体目标、共享契约、共同约束 | 每个执行者 |
| `research-<id>.md` | 调研票首轮 `run --role research --prompt`，交付目录用 `--writable` 放开 | 要核哪些事实、交什么格式的锚点；问事实不问方案 | 调研者 + 你 |
| `brief-<id>.md`（要建 issue 时它就是 issue 正文） | 首轮 `run --prompt` | 单张票的任务书，首段写明真源 | 一个执行者 + 人 |
| `rework-<id>-N.md` | 后续轮 `run --prompt` | 具体哪里不对、证据、期望 | 同一个执行者（线程连续） |
| `REVIEW-<id>.md` | `review --prompt` | 需求口径（前因后果、做到什么程度、有意不做的）+ 关注点 | 复审者（只提意见，你拍板） |
| `accept-brief-<id>.md` | 验收线程首轮 `run --role accept --prompt`，证据目录用 `--writable` 放开 | 复测入口、账号、逐步操作与应看到什么、证据要求、不在范围项 | 验收者 + 你 |
| PR 描述 | `foreman pr --body-file` | 改了什么、风险档、复测入口、项目要求的实测证据 | review 机器人 + 收尾者 + 合并的人 |
| `HANDOFF-<PR>-closeout.md` | `run <id> --closeout --prompt`（实现者续同一线程），或贴给做实现的外部会话 | 收尾任务书 | 实现者（收尾轮） |
| `ACCEPT-<PR>.md` | 报可合时给用户 | 验收包三件 | 亲自验收的人 |

---

## BACKGROUND.md

进的是开发者指令，每个 agent 每轮都要付 token，**只写不写就会出错的东西**。仓库通用规范（`AGENTS.md`）执行者会自己读，不要复述。

```markdown
# 批次背景：<一句话目标>

## 我们在做什么
<2-4 句。为什么做这件事，做完之后系统行为有什么不同。>

## 这批活的整体拆分
- <issue-id-a>: <一句话>（<负责的文件范围>）
- <issue-id-b>: <一句话>（<负责的文件范围>）
你只负责分配给你的那一个。**不要改别人范围内的文件**——同一时刻有别的 agent 在改它们。

## 共享契约（照抄，不要自己发明）
<跨票的类型 / schema / 函数签名 / 表结构 / 事件名，直接贴代码。契约定死，各写各的。>

## 这批活特有的约束
<仅限本批次特殊的。例如"新表尚未落库，先用 X 桩"、"必须复用 Y 而不是新建"。>

## 现状与已知坑
<相关模块当前状态、已知踩过的坑，不要重复踩。>
```

## research-<id>.md（调研任务书：排查交给执行，判断留给你）

```markdown
真源: <要解决的问题从哪来：issue #n | 用户口径「原话」+ 日期>

## 要回答的问题
1. <一个问题一条，问事实不问方案：「读侧在哪一行过滤了 X 题型」「库里 X 类型的 answer 字段长什么样（keys、样本数）」「在途 PR 里谁碰了这些文件、各改了什么」「按 Y 步骤能不能复现、现象是什么」>
2. …

## 看哪里
- 检出：本轮位置给的目录（最新 origin/<base>）；只读
- <数据源：哪个库、只读凭证怎么内联取用、允许的查询范围>
- <在途 PR / issue 从哪拿（gh 入口）>

## 交付物（写到交付目录）
- `FACTS.md`：每个问题一节；每条事实带出处（文件:行号@commit 加前后几行的最小代码摘录、命令与原文输出、查询与结果形状）；「看到的」与「推断的」分开；未核到的单独列
- <需要的话：导出的样本、复现日志>

## 边界
- 只读：不改检出、不 commit、不动数据；<允许 / 不允许的沙箱外动作，点名>
- 不给方案、不下判断；判断题给候选项 + 各自证据
```

**问题写成事实题**：调研者答「在哪、是什么、有多少」，你拿事实拆票、下判断；让它答「该怎么做」就是把判断外派了。验收按阶段 4「调研票的验收」逐条核。

## brief-<id>.md（任务书；要建 issue 时直接作为正文）

```markdown
<项目规则要求的 issue 首行契约，仅当适用时；否则整行删掉，不要编造>

真源: <GitHub issue #n | 文档链接 | 用户口径「原话」+ 日期>   ← 三种都可以；PR 描述里要照抄这一行

## 目标
<一句话说清做完之后什么变了。>

## 背景
<读者不看别处也能开工所需的最小上下文；跨票共享信息放 BACKGROUND.md，这里不重复。>

## 范围
你可以改：
- <路径/文件，尽量枚举到文件>
你不可以改：
- <明确点名容易被顺手改坏的、或属于别的票的>

## 要求
1. <具体行为要求>
2. <具体行为要求>
3. 测试：<写在哪、覆盖什么；按仓库 AGENTS.md 的测试规范>

## 完成定义（机械可判定）
下面每条都必须真的跑过，并在报告里贴出退出码与关键输出：
- [ ] `<type-check 命令>` exit 0
- [ ] `<lint 命令>` exit 0
- [ ] `<具体测试文件的命令>` exit 0，且包含用例 <用例名>
- [ ] <其他可执行断言：某文件存在、某命令输出包含某字符串……>
「既有用例一条都不能挂」按与基线逐条比对兑现：先在未改动的 base 上跑同一条命令记下失败集合，改完再跑，集合必须一致。

## 风险档
低 | 中高   （决定交叉复审跑不跑：低跳过、中高必跑；也决定 review 机器人轮次上限：低 1 轮 / 中高 2 轮）

## 红线
- <这个任务特别容易越界的地方，例如"不要改 schema"、"不要动 contracts/">

## 工作纪律（可选；仓库 AGENTS.md 已有的不重复，只写这张票需要强调的）
- <示例：提交按仓库约定，一个逻辑改动一个 commit，只 `git add <具体文件>`>
- <示例：不确定的地方不猜着实现，写进「需要澄清」>
- <示例：修 bug 先复现、平台配置先查再动；同一问题连改两次不收敛就停下报 PARTIAL>
- <示例：测试命令不要接管道（`test | grep` 会吞退出码），退出码按命令本身的>
- <示例：验证日志写到工作树之外（`/tmp` 或编排者指定目录），不要留在仓库目录里>
- <示例：项目对用户可见文案的语言 / 风格要求>
```

**完成定义写不出来 = 这张票不该派。** 避免假条目：`代码质量良好`（不可判定）、`测试通过` 而不说哪个、只写全仓 `test`（慢且噪音大，指到具体包和文件）。

## rework-<id>-N.md

线程是连续的，执行者记得上一轮，**不要重复整个任务书**。

```markdown
## 你上一轮的问题
<按严重度排序，每条给证据>

1. <问题一句话>
   证据：
   ```
   <失败命令的真实输出原文，不要改写>
   ```
   位置：<file:line>
   期望：<具体应该是什么行为>

## 这一轮只做这些
<明确本轮范围，防止它顺手重构别的地方>

## 完成定义不变
重新跑一遍原来那几条命令，全部贴出退出码与输出。
```

**只说「还是不对」等于花额度买另一次猜测。**

## REVIEW-<id>.md（给复审者的需求口径 + 关注点；`foreman review <id> --prompt` 传入）

复审者没有你的上下文，判不了「需求做对没有」；它的活是对抗性视角：这次改动有没有破坏项目约定、仓库约定、最佳实践。所以这份文件**首段是需求口径**，没有它复审者只能对着 diff 猜、把权衡后的边界当遗漏报。它给的是意见，采不采纳你逐条拍板。

```markdown
## 需求口径（复审者最需要的上下文）
- 为什么做：<前因，问题从哪来>
- 做到什么程度：<这次要做到的、多方权衡后的边界>
- 有意不做的：<明确排除的，别当遗漏报>
- 风险档：低 | 中高

## 关注点（可选；默认按角色文件里的清单看）
<本票特有的：例如"动了写路径，重点看幂等与并发""这里的约定见仓库 AGENTS.md 第 N 节"；要额外的节（如测试有效性抽查）也写在这里>
```

**只提意见，不下判决**：复审者的每条意见带依据（哪条项目 / 仓库约定、哪个最佳实践、什么输入会出错）；你逐条判采不采纳，采纳的进返工任务书。

## accept-brief-<id>.md（验收任务书：把产品真跑起来对清单看；不要叫 `accept-<id>.md`——交付物 `ACCEPT-<PR>.md` 在大小写不敏感的文件系统上会把它覆盖）

```markdown
真源: <PR #n + 任务书路径 + 用户口径>

## 复测入口
- <预览 / 测试环境 URL 或本地起服务的命令；用哪个账号（凭证内联取用）；写入会落到哪个库>

## 逐项验收（做什么 → 应该看到什么）
1. <步骤> → <应看到>；证据：<截图名 / 输出>
2. …
只判本 PR 触碰的面；批次外既有问题只记不判。

## 证据要求
- 截图 / 命令输出落交付目录，文件名标步骤号与 head sha

## 边界
- 不改代码、不修问题：发现问题写现象 + 复现步骤 + 证据，不动手修
- <允许的沙箱外动作，点名：测试专用浏览器 / cdp 脚本、查测试库只读…>

## 交付物
- 填好的 `ACCEPT-<PR>.md`（模板见下）+ 逐项结果表（通过 / 不通过 / 未能验证 + 证据路径）
```

实现真源: <GitHub issue #n | 文档链接 | 用户口径「原话」+ 日期>   ← 每个 PR 必写，验收和复审对着它核

## 改动
- <按用户面而不是按文件列>

## 复测入口
<收尾者 / 验收者从哪个页面、哪条命令进入；用哪个账号；写入会落到哪>

## HANDOFF-<PR>-closeout.md（收尾任务书）

收尾阶段契约（`assets/CLOSEOUT.md`，`--closeout` 自动放在 prompt 顶部）只给远端动作白名单和输出格式；**怎么处理 review、几轮、按什么判，全在这份里**。实现者续同一线程，它记得任务书与自己的改动，不用重述。

```markdown
# 收尾任务书：PR #<n>（<一句话>）

> 目标：处理 review findings → 同步 base → 描述同步 → `pr ready`。**不 merge**。<日期时间，先 `date`>写。

## PR 事实
- PR 链接、head sha、draft/ready、base、worktree 路径（你仍是这条分支唯一的执行者）
- CI 现状；已闭环的 review 轮次与判定；已知与本 PR 无关的红
- 风险档：低 / 中高 → 本次最多处理 N 轮
- 主会话已判过、**不用再问**的取舍清单

## 工作循环
等 CI → 读 review → 逐条判断 → 修（攒齐一次 push）→ 回复并 resolve → 再等 CI。不必每轮请示；只有需求边界或业务口径要变时停下来问。
1. 两处都要读：inline review thread，以及被路由进 PR summary 评论、没有 thread 也没 resolve 按钮的条目。每次 push 都会触发新一轮 review。
2. 不默认采纳：逐条结合任务书口径、整体架构、真实执行路径和测试证据判断；只有问题真实成立、且改动的整体收益明确大于风险时才改。明确无效、过期、超出本 PR 范围的可以不改，但要说明依据。
3. 轮次：一轮 = 一次 push 触发并跑出结论的 review；同步基线的 merge push 不算。低风险只修确认成立的 high / medium；中高风险第 2 轮只修第 1 轮修复本身引入的新 high / medium。low / nit / 风格 / 超范围重构建议一律回复判断并 resolve，不为它们再 push。到上限仍有未决项：列表（位置 / 严重度 / 判断 / 建议处置）停下来交编排者，不自动进下一轮。
4. 修与不修都闭环：改了的说明改动与验证并注明 commit；不改的说明依据。inline 条目回在 thread 里并 resolve；summary 条目回在 PR 评论里。每处理完一批发一条表格评论（位置 / 结论 / 依据）。
5. 同步基线：base 有新合入时 `git merge origin/<base>`（不 rebase），解完冲突重跑相关验证再 push。语义冲突（另一条 PR 改了名、删了词条、改了签名）当真实问题修，不占轮次。
6. PR 描述同步：描述必须与最终改动一致；「复测入口」「实测」等节核对内容还是不是真的。
7. 报「可合」之前重数：以当前 head 触发的那一轮为准，用 API 重新数 unresolved thread、重读最新 summary。CI 绿不等于 review 已读；review job 绿不等于 0 findings。
8. 没有 CI run 不等于在排队：PR 一个 run 都没有时先查是否与 base 冲突（不少仓库的 feature 分支只走 pull_request 触发，冲突就不跑），解完冲突再等。
以上是 skill 的最佳实践口径；项目规则另有说法以项目规则为准。

## 本 PR 特有
<最后一轮 review 的处理口径；同步 base 的注意点；描述要核对的节；项目特有事实，例如"必需检查有哪些""review 机器人是哪个、结果在哪看">

## 纪律
gh 入口用 <路径>；只 push 本分支、禁 force；不动别的 worktree；凭证不回显；提交按仓库约定、作者用 worktree 配置身份、只 `git add <具体文件>`。

## 回报
按收尾阶段契约的输出格式：head sha、判定表、未决项表、ready 状态、拿不准的点。
```

## review 判定表（收尾者每批一条评论）

| 位置 | 严重度 | 结论（采纳 / 不采纳 / 部分） | 依据 / 修复 commit |
| --- | --- | --- | --- |
